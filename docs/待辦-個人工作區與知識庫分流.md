# 待辦規格：個人工作區、知識庫分流與向量檢索、計算問題

> 2026-11-04 與使用者確認的需求與決定。**三個階段都已完成並驗證（2026-11-04）**，使用說明見根目錄 README 的「個人工作區」「知識庫分流與向量檢索」「計算問題」「員工助理全功能」「測試與驗證」。
>
> 實作時與原規格的差異：Google 日曆同步做成「管理員的全域選用開關」（預設關），沒有做成每個人各自的選項；舊的客戶追蹤日在 `setup` 時一次性遷移進內建行事曆；員工助理除了行事曆 / 工作清單，也一併補齊產品 / 詢價 / 客戶窗口 / 案件內容 / 文案等功能。

## 已確認的決定
- 行事曆：**系統內建**（事件存在試算表），每個帳號各自獨立，不再依賴那個共用的 Google 日曆。
- 群組：**系統管理員在「帳號管理」建立與管理**（群組名稱 + 成員）。
- 分享權限：**只能查看**（只有擁有者可以編輯、刪除）。
- 知識庫：**不用外部向量資料庫服務**，向量存在試算表，由機器人伺服器（Vercel）算相似度。

## 階段 A：個人工作區（行事曆 / 備忘錄 / 工作清單）
**需求**：每個帳號都有獨立的行事曆、備忘錄、工作清單；行事曆可選擇公開給：自己、多人、自訂群組、全部。

### 資料表（Code.gs 新增）
- `CalEvents`：ID, Owner, Title, StartDate, StartTime, EndDate, EndTime, AllDay, Location, Notes, ShareMode, ShareWith, Source(manual / followup), RefKey, CreatedAt, UpdatedAt
- `Todos`：ID, Owner, Title, Notes, DueDate, Priority(高/中/低), Status(todo / doing / done), ShareMode, ShareWith, CreatedAt, UpdatedAt, DoneAt
- `UserGroups`：ID, Name, Members(帳號 JSON 陣列), CreatedBy
- `Memos`（既有）加欄位 `ShareMode`、`ShareWith`（`Shared=是` 舊資料視為 ShareMode=all）
- ShareMode：`self`（預設）/ `users`（ShareWith = 帳號陣列）/ `groups`（ShareWith = 群組 ID 陣列）/ `all`

### 規則
- 讀取：自己的 + 被分享給我的（直接指定我、我所屬群組、全部）。
- 寫入 / 刪除：只有擁有者（系統管理員可處理他人資料）。
- 個人資料不走功能區塊權限（登入就能用自己的），分享也不放寬他人的編輯。
- 客戶「下次追蹤」自動寫入**負責人（操作者）自己的行事曆**（Source=followup），改期 / 不再追蹤時同步更新或刪除；Google 日曆同步改為選用開關（預設關），舊資料遷移一次。

### 畫面
- 業務行事曆頁：月 / 週 / 清單檢視，切換「我的 / 別人分享給我的」，建立事件時選公開對象。
- 首頁：行事曆卡片改讀自己的；新增「工作清單」卡片與獨立頁面。
- 帳號管理：新增「群組」分頁（建立、改名、設定成員）。
- 員工助理（Code.gs BotStaff 章節）：`list_calendar`、`list_memos` 改讀個人與被分享的；新增 `list_todos`；提出修改可新增事件 / 工作（仍需本人確認）。

## 階段 B：知識庫分流 + 向量檢索（客服機器人）
**需求**：後端設置「大分類、主題、備註、向量資料」；搜尋流程可設定；向量要有分數閥值。

### 知識庫欄位（BotKnowledge 新增）
- `BigCategory`（大分類）、`Topic`（主題）、`Notes`（備註：寫給 AI 看，方便分流）、`Vector`（向量 JSON；太大時另存 `BotVectors` 分頁）、`VectorModel`、`VectorAt`
- 新增 / 修改 / 匯入時自動計算向量；另有「重新計算全部向量」按鈕（顯示進度、可中斷續跑）。
- 向量來源：embedding API（預設沿用 BOT 設定的 AI 金鑰，Gemini / OpenAI 相容；Claude 沒有 embedding，會提示改用別家）。

### 搜尋流程（BOT 設定 → 知識庫 → 搜尋流程）
| 模式 | 說明 |
|---|---|
| 直接向量（預設） | 全部段落用向量相似度排序 |
| 先中繼再向量 | 先用「大分類 / 主題 / 備註 / 標題」比對縮小範圍，再在範圍內做向量檢索 |
| 只用中繼資料 | 只用「大分類 / 主題 / 備註 / 標題 / 關鍵字」檢索，不用向量 |
| 兩種都做，結果一致才回答 | 中繼檢索與向量檢索各做一次，兩邊都命中的段落才拿來回答；沒有交集就請客人換個說法或轉真人 |

- **向量分數閥值**可調（0～1，預設 0.6）：低於閥值的段落不採用；全部低於 → 走「找不到答案」流程。
- 可調：取前幾段、各欄位比對權重。
- 後台「搜尋測試」：輸入問題，顯示每種模式找到的段落與分數，方便調閥值。

### 實作位置
- Code.gs（BOT 章節）：欄位、向量計算 / 儲存、`csKnowledge_` 回傳新欄位與向量、搜尋設定。
- `linebot/src/rag.ts`：四種流程、cosine 相似度、閥值；`linebot/src/ai.ts` 新增 `embed()`。
- 向量快取在伺服器記憶體（同知識庫快取 5 分鐘）。

## 階段 C：計算問題（選型計算）
**需求**：使用者問的是計算問題（如選型計算）要算出來，並整理重述客戶要的計算，避免錯誤。

### 做法
- 把網站「選型計算」的公式（`frontend/calc.js`）移植成 `linebot/src/calc.ts`，用現有測試案例核對兩邊結果一致。
- 給 AI 一個 `calc_selection` 工具，參數是結構化的需求（檢測範圍 W×H、最小檢測精度、單特徵像素數、工作距離…）；AI **不自己心算**，一定呼叫工具。
- 回覆順序固定：①「我整理你的需求是：…」（列出每個參數與單位，缺的欄位先反問，不猜）→ ②「計算結果：…」（附算式）→ ③ 建議的相機 / 鏡頭型號（來自知識庫的產品規格，不含價格）。
- 單位換算（mm / µm / 吋）、方向（長邊 / 短邊）等容易出錯的地方，工具裡明確處理並回報用了哪個假設。
- 客服機器人與員工助理都可用；客服版不顯示任何價格。

## 建議順序
1. **階段 B**（知識庫分流與向量）：直接影響客服機器人的回答品質，也是正式上線前最值得先做的。
2. **階段 C**（計算問題）：規模較小，可獨立完成。
3. **階段 A**（個人工作區）：改動資料表與多個頁面，最後做，做之前先備份試算表。
